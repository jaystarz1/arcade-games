Asteroids Clone – Product Requirements Document

Project Overview

The goal of this project is to create a faithful clone of Atari’s 1979 Asteroids arcade game as a persistent web application. The game will replicate the original’s gameplay, vector graphics style, and features as closely as possible. This includes matching the look, feel, and behavior of the classic game (ship movement, asteroid splitting, UFO behavior, scoring, etc.) while making the game playable on modern web browsers (desktop and mobile). Because this is for personal (non-commercial) use, we aim for an exact copy of the original Asteroids in terms of visuals and mechanics.

Key Objectives:
	•	Authentic Gameplay: Recreate the original game mechanics – the player controls a single triangular spaceship in an asteroid field, shooting asteroids and flying saucers while avoiding collisions and enemy fire ￼.
	•	Original Look and Feel: Use vector-style graphics (line drawings on a black background) to mirror the original’s distinctive visual style ￼. The game should look and behave the same as the late-70s arcade version.
	•	Cross-Platform Web App: Implement as an offline-capable web application (HTML5/JavaScript) that runs smoothly in modern browsers. It should be persistent (playable without internet after first load) and mobile-friendly (adapted controls/UI for touch screens).
	•	Full Feature Parity: Include all original game features: wrapping playfield, inertia-based ship movement, hyperspace jump, two types of UFOs, original scoring system, extra lives, and even the “heartbeat” audio that speeds up as the game progresses ￼.
	•	High Fidelity Audio: Incorporate the same sound effects and background sounds as the original game (thrust sound, shooting “pew”, explosion, UFO sounds, etc.), since this is a personal project and original audio can be used if available.

By adhering to these goals, the finished product will essentially be Asteroids as one remembers it, packaged as a modern web app suitable for desktop and phone deployment.

Gameplay Mechanics

Player Ship & Movement
	•	Ship Controls: The player controls a single triangular spaceship that can rotate left or right, thrust forward, and fire shots from its nose ￼. The ship’s orientation is independent of its velocity; for example, you can be drifting in one direction while facing another.
	•	Momentum & Inertia: Once the ship is set in motion by thrusting, it will continue moving in the last direction of thrust (simulating inertia in space). In the original game, the ship gradually slows down and eventually stops if no thrust is applied, due to a small friction/damping factor in the physics ￼. We will implement a slight velocity decay so the ship isn’t perpetually drifting without input (to match the arcade behavior).
	•	Thrust: Activating thrust (forward propulsion) increases the ship’s velocity in the direction it is currently facing. For the clone, each thrust action will add a fixed increment to the ship’s speed (in the original, e.g., ~0.5 px/frame acceleration in its direction). The ship’s maximum speed will be capped to maintain control.
	•	Rotation: The ship rotates on its center. We will use a fixed rotation speed per frame when the left or right turn control is held. (Original Asteroids rotated ~6 degrees per frame on each button press in the arcade ￼; our clone will use a similar turn rate to ensure responsive maneuvering.)
	•	Wrapping Playfield: The game field wraps around in both axes – if the ship (or any object) goes off one edge of the screen, it reappears on the opposite side at the same trajectory ￼. This means the game world is topologically a toroid (no walls). The playfield will be two-dimensional and likely set to a fixed size (we will use an aspect ratio similar to the arcade’s display). For example, if using an internal coordinate system, we might set it to ~1000px width by 800px height (4:3 aspect) and scale to the screen. Wrapping will be implemented by checking boundaries: if an object’s position exceeds the max X/Y, it will be wrapped to the other side.
	•	Collisions: If the ship collides with an asteroid or saucer (or gets hit by a saucer’s bullet), the ship is destroyed. In our implementation, we will treat the ship as a circle (for collision detection) of roughly radius ~10 units ￼, and asteroids as circles of radius proportional to their size (e.g. ~16 for large, 8 for medium, 4 for small) ￼ ￼. A collision occurs when the distance between centers is less than the sum of radii. Upon collision with the ship, we will trigger an explosion effect and subtract a life.
	•	Hyperspace Jump: The ship can perform a hyperspace jump (teleport) as a panic escape. When triggered, the ship disappears and reappears at a random location on screen, with its velocity reset to zero ￼. However, this comes with risk – in the original game there was a chance (~1 in 4) that the ship would explode on re-entry or appear on top of an asteroid, instantly losing a life ￼ ￼. We will replicate this by implementing a probability of ship destruction on hyperspace (e.g. 25% base chance), possibly increasing if the space is very crowded (to mimic the original’s behavior where jumping into a busy screen was more dangerous). The hyperspace feature will be used sparingly by players (last resort), so we will include it for authenticity.

Asteroids
	•	Asteroid Types: There are 3 sizes of asteroids: Large, Medium, and Small. All asteroids are rendered as irregular polygonal outlines (vector line drawings). Large asteroids drift slowly, medium asteroids move faster, and small asteroids are the fastest and hardest to hit ￼.
	•	Initial Wave: Each level (wave) begins with a set of large asteroids drifting in from the screen edges. On the first wave, the game typically starts with 4 large asteroids by default ￼ (some versions/settings allowed 6 as a harder starting difficulty ￼, but we will use 4 as the standard). These asteroids start at random positions and move in random directions.
	•	Asteroid Splitting: When a large asteroid is shot, it breaks into two medium asteroids; when a medium is shot, it breaks into two small asteroids ￼. Shooting a small asteroid destroys it completely (it disappears with no further progeny) ￼. The smaller the asteroid, the faster it moves – this increases difficulty as you break rocks apart. We will implement this by replacing the asteroid object with new smaller asteroid objects, assigning them appropriate higher velocities. For example, if a large asteroid (slow) is destroyed, we spawn two mediums that inherit the large asteroid’s velocity plus a random slight additional velocity (in original, one medium got a velocity boost upward, one downward ￼). Similarly, medium asteroids spawn two small ones (with small random velocity offsets). The direction of the new asteroids can be predetermined (e.g., one goes to the left, one to the right) or random, but ensure they spread out.
	•	Asteroid Movement: Asteroids drift in straight lines with constant velocity (no acceleration). They also rotate slowly in place as they drift, purely for visual effect. In the original, a large rock rotated ~2° per frame, medium ~5°/frame, small ~10°/frame ￼ ￼. We will use similar rotation rates to give each asteroid a tumbling appearance. Rotation does not affect their trajectory, it’s just the polygon spinning about its center.
	•	Wrapping: Asteroids also wrap around screen edges. So an asteroid leaving one side will re-enter from the opposite side, maintaining seamless motion across boundaries ￼.
	•	Level Progression & Difficulty: Once the player destroys all asteroids (and saucers) on the screen, the level is cleared. A new wave begins with a larger number of large asteroids. Specifically, after the first wave of 4 large asteroids, the next wave might have 6 large asteroids, then 8, and so on – the original game added 2 extra large asteroids each wave up to a maximum of 11 large asteroids by around wave 4 or 5 ￼. We will follow this progression (4, 6, 8, 10, 11, 11, 11, … on subsequent waves). This means later levels start with a screen densely packed with asteroids, increasing difficulty.
	•	Asteroid Count Cap: In the original hardware, there was a limit of ~26–27 asteroids on screen at once due to memory limits ￼. If the player delayed destroying asteroids and the screen got extremely full, any additional asteroid that should spawn would simply not appear (or a large asteroid might split into just one medium instead of two if the cap was reached ￼). For our clone, performance is the main consideration. We will set a reasonable cap (we can allow more than 26 if performance permits, but realistically even with 11 large asteroids fully split, the maximum total asteroids on screen would be: 11 large -> split into 22 mediums -> split into 44 small, but they wouldn’t all exist simultaneously because you must shoot them in stages. The peak is usually when a wave starts and during splitting). We will ensure the game runs smoothly even at the highest asteroid counts; if needed, we might cap the total active asteroids to, say, 50, though in normal play it won’t exceed the original limits.
	•	Collision Behavior: Asteroids can collide with the player’s ship (destroying the ship) or with flying saucers (destroying the saucer) – however, asteroids do not collide with each other in this game (they pass through each other). We will not implement inter-asteroid collisions (this matches the original, which treated them as obstacles for the player only). When an asteroid is hit by a bullet, it breaks as described; when it hits a ship or saucer, the asteroid remains intact (in original, a saucer hit by an asteroid would result in the saucer exploding and the asteroid continuing unaffected ￼). We will mimic that: asteroids are only destroyed by being shot, not by crashing into something (except maybe if we want to simulate an asteroid being “bombed” by a saucer’s bullet – original saucers could shoot asteroids, breaking them, which did happen occasionally ￼. We will include that: saucer bullets will have the same effect on asteroids as player bullets).

Flying Saucers (UFOs)
	•	UFO Types: The game features two types of enemy saucers that appear periodically: a “Large Saucer” and a “Small Saucer.” They serve as additional hazards and targets for points.
	•	Behavior & Difficulty:
	•	The Large Saucer moves slowly across the screen (generally appearing from a random edge) and fires bullets at random directions (its aim is poor) ￼. It is less dangerous and appears in earlier stages.
	•	The Small Saucer is smaller, moves faster, and fires more frequently with aimed shots at the player ￼. Its aim becomes very accurate as the player’s score increases, making it a serious threat in later gameplay ￼. At lower scores, the small saucer still tries to target the ship but with some inaccuracy (we will implement a firing algorithm that aims towards the player with a random angular deviation – the deviation will shrink as the score or level increases, simulating improved accuracy).
	•	Spawn Frequency: Saucers appear after the game has been in progress for a short time and then at intervals. Typically, a saucer might spawn every ~20–30 seconds if the level isn’t cleared. In the original, the spawn rate and which type of saucer appears depends on the player’s score: below a certain score threshold, mostly large saucers appear, but as the score grows, small saucers appear more often, and beyond ~40,000 points only small saucers appear ￼. For our implementation, we can simplify: for the first few waves or until the player hits 10,000 points, spawn mostly large saucers; afterwards, favor small saucers. After a high score (e.g. 40k), exclusively spawn small saucers for challenge.
	•	Movement: Saucers will fly horizontally across the screen (occasionally with a slight vertical drift). They will wrap around the screen edges as well – if a saucer exits one side, it might re-enter from the other after a delay (though in the original, typically a saucer that leaves is gone and a new one spawns later; we can simulate it either way). We will likely despawn a saucer after it has been on screen for a certain time or after it leaves the bounds, then timer for the next spawn.
	•	Shooting: Both saucer types fire projectiles similar to the player’s bullets (small fast shots that also wrap around edges). The large saucer fires in random directions (not necessarily towards the player, which often results in wild shots) ￼. The small saucer, on the other hand, will attempt to shoot at the player. We will calculate a trajectory from the saucer to the player’s current position (or predicted position, to simulate leading the target if we want an extra challenge) with some random offset for lower accuracy. As difficulty increases, the randomness is reduced. In the original code, after ~35k points the small saucer’s shot spread narrowed significantly, making it deadly accurate ￼.
	•	Destruction: One hit from a player’s bullet will destroy a saucer. Also, as mentioned, if a saucer inadvertently collides with an asteroid, the saucer is destroyed (and the asteroid remains) ￼. We will implement saucer destruction in both cases. On destruction, a saucer should produce an explosion effect and award points to the player.
	•	Points: Shooting saucers gives the player points:
	•	Large Saucer is worth 200 points ￼ ￼.
	•	Small Saucer is worth 1,000 points (the original display showed 1000 as  “1000” – internally 990 due to how the score was stored in BCD ￼, but effectively one thousand) ￼.
	•	We will use the same values: 200 and 1000, respectively.
	•	Frequency and Limits: Only one saucer can be active at a time. We will ensure that at most one UFO is on screen; if the player destroys it, the timer for the next one starts. In the original, after the player reaches a certain score (~10,000 points), the small saucer becomes a permanent threat, meaning one will appear soon after the previous is destroyed (“the small saucer becomes a permanent part of the game” after 10k points ￼). We will mirror this: at high scores, basically a new small saucer spawns almost immediately or with minimal delay after one is destroyed, keeping pressure on the player. In early stages, there might be a longer breather between saucers.

Bullets & Firing
	•	Player Shots: The player can fire projectiles (bullets/missiles) from the ship’s front. In our clone, pressing the Fire button/key will spawn a bullet at the tip of the ship’s triangle, initially moving in the same direction the ship is facing (and it inherits the ship’s current velocity as well, plus an additional firing speed). For example, if the ship is moving, the bullet’s velocity = ship’s velocity + a fixed speed (original Asteroids gave the bullet an extra ~5 px/frame in the ship’s facing direction on top of the ship’s own motion ￼).
	•	Fire Rate & Limits: To replicate the original’s challenge, the number of bullets the player can have on screen at once is limited. The original game allowed no more than 4 shots to exist simultaneously ￼. If the player fires when 4 bullets already exist, the input is ignored until a bullet despawns. We will implement this 4-shot limit. The firing rate is effectively governed by this limit and bullet lifespan – the player can tap rapidly, but if they spam too fast, they might reach 4 shots and then have to wait for one to disappear. We will allow a modest rate of fire; the original hardware could register about 1-2 shots per second if you hammered the button, since shots persisted a moment. Our clone might allow a slightly faster fire input but still cap at 4 active shots.
	•	Bullet Lifespan: In order to prevent bullets from flying indefinitely (which would eventually clutter the game or hit something after many wraps), bullets will have a finite lifespan. In the arcade game, a shot would disappear after it traveled a certain distance or time (in many Asteroids clones, bullets live for ~1 second or until they have traversed the screen bounds a certain number of times). We will implement a lifespan (for example, ~40 frames (~2/3 of a second at 60 FPS) as suggested in some Asteroids implementations ￼). After that, the bullet will disappear if it hasn’t already hit something. This means the player cannot just fire and have bullets circling forever; they must aim timely shots.
	•	Bullet Wrapping: Just like all other objects, bullets wrap around screen edges ￼. A shot that goes off the left edge will re-enter from the right, etc. This allows skilled players to shoot across the screen wrap (even hitting a saucer that’s on the opposite side by shooting the edge). We will ensure the bullets maintain their path through wraps seamlessly.
	•	Collision & Damage: A bullet hitting an asteroid will split or destroy the asteroid (as described above) and the bullet itself will be destroyed in the process. A bullet hitting a saucer destroys the saucer (and the bullet is removed). If a bullet somehow hits the player’s ship (for instance, a saucer bullet or your own bullet after multiple wraps – though you cannot shoot yourself in the original as shots don’t wrap instantaneously and you outrun your bullets), it will destroy the ship. We will check bullet collisions against asteroids, saucers, and the ship (for enemy bullets). Collision detection for bullets can be done by checking distance to object centers (since bullets can be treated as points or very small circles). Given the high speed of bullets, we will run collision checks each frame and possibly use small bounding radii for collision (like radius ~1-2 for bullets).
	•	Visuals: Bullets are drawn as small dots or short line segments. In the original Asteroids, bullets were drawn as points of light (single pixel points that are very bright). For our clone, we can draw them as small circles or 2px lines. We will ensure they are clearly visible (bright white) and perhaps draw a brief trail if needed for visibility on high-res displays.

Scoring, Lives & Progression
	•	Scoring System: The game’s scoring follows the exact scheme of the original:
	•	Large Asteroid: 20 points ￼ ￼
	•	Medium Asteroid: 50 points ￼ ￼
	•	Small Asteroid: 100 points ￼ ￼
	•	Large Saucer: 200 points ￼ ￼
	•	Small Saucer: 1,000 points ￼ ￼
We will implement the scoring exactly as above. Points are awarded immediately when an object is destroyed by the player. The score will be displayed on screen (typically top left or top center, as in the arcade).
	•	Lives: The player starts with 3 ships (lives) by default ￼. (We may allow this to be configurable between 3 and 5 to match the original DIP switch settings ￼, but 3 is the standard.) Each time the player’s ship is destroyed, one life is lost. When lives reach 0, the game is over.
	•	Extra Lives: The player earns an extra life every 10,000 points scored ￼. This will be indicated by incrementing the reserve ships. We will implement this exactly (score threshold for bonus lives = 10,000). A sound effect will play when an extra life is awarded (the original played a distinct sound whenever you crossed 10k).
	•	Level Progression: The game is essentially endless; it progresses in waves of increasing difficulty until the player loses all lives. After clearing each wave of asteroids (and any active saucer), a new wave starts with more asteroids as noted. We will likely indicate the wave number subtly (perhaps not onscreen, as the original didn’t explicitly label levels, but we could keep count internally or display it between levels or as part of a debug overlay).
	•	Difficulty Increases: As waves increase:
	•	More asteroids at start (harder to survive the initial moments).
	•	Saucers appear more frequently and are more often the deadly small type at higher scores.
	•	The background “heartbeat” sound (see Audio section) speeds up when fewer asteroids remain in a wave, creating tension.
	•	The small saucer’s accuracy increases with score (we will map this such that by ~40k or so, it’s extremely accurate, matching original behavior ￼).
	•	Asteroid speeds might already be inherently higher by having more small asteroids flying around in later waves. We won’t artificially speed up asteroids per level beyond the sizes (original game did not increase asteroid base speeds per level, it just throws more of them at you).
	•	Game Over and High Scores: When the player loses the last life, the game ends. The player’s final score is compared to the high score list. In the original arcade, if it was a top score, the player could enter their initials. We will include a High Score table locally, since this is a personal game but one may still want to track best performances or share with friends. The clone will maintain a list of top scores (with initials or name entry for each) in the browser’s local storage. Notably, Asteroids was one of the first games to let players enter their initials for high scores ￼. We will honor that tradition by prompting the player for initials when they achieve a new high score.
	•	Score Rollover: One authentic detail – the original score display was 5 digits, and it would “roll over” at 99,990 (scores above that would wrap around to 0) ￼ ￼. In our clone, we can either simulate a 5-digit score for nostalgia or simply allow an extended score. As this is personal use, we might allow the score to continue past 99,990 (modern displays have no such limitation). However, we could still cap or indicate the rollover for authenticity. Perhaps we’ll display 6 digits (so it rolls at 999,990, which is less authentic). For a true exact copy feel, we could cap the on-screen score at 99,990 (e.g., display last 5 digits) but still track the true score behind the scenes. We’ll note this as a design decision – likely we will remove the rollover limit for practicality, but it’s an option to include a “turn-over” easter egg if desired.

Controls and User Input

Because we want the game to be playable on both desktop (keyboard) and mobile devices (touchscreen), we will implement multiple control schemes:

Desktop Controls (Keyboard)

On desktop/laptop, the controls will mirror the original arcade button layout:
	•	Rotate Left: Use the Left Arrow key (←) to rotate the ship counter-clockwise ￼.
	•	Rotate Right: Use the Right Arrow key (→) to rotate the ship clockwise ￼.
	•	Thrust: Use the Up Arrow (↑) to engage forward thrust (propel the ship forward).
	•	Fire: Press the Spacebar to fire a shot. (In the original, the “Fire” button was separate; we choose space for convenience. Alternate: the Ctrl key was used in MAME setups ￼, but spacebar is more universal on web.)
	•	Hyperspace: Press the H key (or possibly Shift or Alt) for Hyperspace jump. We will choose a key that doesn’t conflict with browser shortcuts – for instance, H for hyperspace is simple. (Original arcade had a dedicated Hyperspace button; MAME defaults use Space for hyperspace ￼, but since we are using Space for fire, we assign H for hyperspace).
	•	Start/Pause: Since this is a web game, we will include a Start/Pause toggle. Pressing P could pause/unpause the game (original arcade had a physical start button and no pause, but as a personal modern version, pause is useful). The Escape key can quit the game or return to a menu if we have one (in development or debug mode) ￼.

These keys will be documented in the UI (e.g., an on-screen help or in the README). They allow simultaneous input (e.g., holding rotate and thrust while tapping fire). We will implement responsive key handling so multiple keys can be pressed at once with no lag (e.g., using keydown events and tracking the set of keys pressed to allow smooth turning while firing).

Mobile/Touch Controls

On touch devices (phones, tablets), we will provide on-screen controls since there is no physical keyboard. The design will be optimized for two-thumb gameplay (similar to how many mobile games place a “virtual joystick/pad” on the left and buttons on the right):
	•	Rotation (Left/Right): On the left side of the screen, we will display two touch regions or buttons – a left arrow and a right arrow. Pressing these will rotate the ship left or right respectively. These can be semi-transparent overlays of arrow icons. They will be positioned for easy reach by the left thumb (for example, bottom-left corner for rotate left, just above or next to it for rotate right).
	•	Thrust: On the right side of the screen, we will have a button (perhaps an up arrow icon or a flame icon) for Thrust. This will be placed near the bottom-right where the right thumb can hold it. The user will typically press this to move forward【user’s requirement†】.
	•	Fire: Also on the right side, we will include a Fire button. For instance, a round “shoot” button could be placed a little above the thrust button or to its left, so it can be tapped with the right thumb as well. This allows the player to press thrust and fire nearly simultaneously with one thumb (one can quickly alternate or even multi-touch if possible).
	•	Hyperspace: If we include a hyperspace button on mobile, we have a few options: (a) a smaller button on the right side (since hyperspace is used rarely, maybe a smaller icon above the fire button), or (b) a gesture like a two-finger tap anywhere to trigger hyperspace (to avoid cluttering the screen with too many buttons). We will likely implement a small hyperspace button in a corner (maybe bottom-right corner above thrust) for completeness.
	•	Layout and Feedback: The touch controls should be visible enough to use but not distracting. We will possibly make them semi-transparent and only in the corners. Additionally, they should respond to multi-touch (e.g., the player should be able to hold down thrust and simultaneously tap fire, or hold rotate and thrust together). We’ll ensure the touch event handling allows concurrent inputs.
	•	Customization: Because screen sizes vary, we’ll use relative positioning (percent of screen) for these controls. We might also allow the player to adjust the size of the touch controls (e.g., small, medium, large button sizes) for comfort, but default will be ergonomic for a typical phone in landscape orientation.
	•	Orientation: The game will play best in landscape orientation on phones (wider view makes it easier to see asteroids and provides space for controls on the sides). We will encourage landscape by design. If the user is in portrait, we may either restrict to landscape (lock orientation if possible) or provide an alternate control layout (e.g. arrows at bottom left/right and thrust/fire bottom right). For simplicity, we target landscape play.
	•	Responsive Design: The canvas (game screen) will scale to fit most of the viewport, and the control overlays will sit on top. On a tablet or larger screen, the controls might appear further outwards so as not to obscure the playfield.

All controls (keyboard or touch) will be thoroughly tested to ensure the game feels responsive and true to the arcade experience. For example, rotation should be smooth, not too slow or too fast to overshoot, thrust should feel similar to the original momentum, and firing should be reliable with the 4-shot limit clearly observable.

Graphics and Visual Design

*Figure: Screenshot of the original Asteroids (1979) gameplay, demonstrating the black background and monochrome vector line graphics (the player’s ship is the small triangle at center, with asteroids as irregular outlines)＊

The visual style will be a key focus to make our clone look as close to the original as possible:
	•	Vector Graphics: Asteroids was a classic vector display game – all graphics were drawn with lines (wireframes) on a black screen, rather than raster sprites. We will recreate this by using line-drawing routines (e.g., HTML5 Canvas API or WebGL line primitives) to draw all game elements as wireframes. The ship, asteroids, and saucers will be outlined shapes (no fills). This gives the crisp, geometric look of the original. According to documentation, the game’s vector monitor drew vivid glowing lines for the graphics ￼. We may simulate a slight glow: for instance, drawing the lines in bright white (#FFFFFF) and perhaps drawing them twice to intensify brightness, or using a subtle blur effect, to mimic the luminous quality of real vector monitors. This is a polish item; at minimum, solid white lines on black will suffice for the look.
	•	Asteroid Shapes: The asteroids should have the same “random rock” appearance as the arcade. In the original, a few irregular polygon shapes were predefined (each asteroid could be one of several shapes) – jagged, roughly circular outlines. We will either use a set of predefined polygon vertex patterns (perhaps 4-5 unique shapes for variety) or generate random polygon shapes each game. The shapes should have 10-16 vertices with varying radial distances to look jagged (but no sharp spikes that look unlike the original). These will be scaled appropriately for large/medium/small sizes. They will rotate as they move. We’ll ensure the scaling and line thickness keep them looking like the original (large asteroids appear larger obviously, small ones about one-quarter size of large).
	•	Ship Design: The player’s ship is a simple outline of a triangle (essentially a wedge-shaped spacecraft). We will draw it as a triangle with a small notch or two lines for detail if needed (the original was basically two slanted sides and a flat back, forming a pointed front). We might implement the ship drawing via code (moving a path to draw a triangle) or use a small vector shape template. The ship’s size will match original proportions relative to asteroid size (roughly the size of a small asteroid). We will also draw a small flame coming out the back when thrust is active – in the original game, thrust was indicated by a little thrust flame animation at the rear of the ship. We can simulate this by toggling a flame shape (like a small flickering triangle) when thrust is on.
	•	Saucer Design: The UFOs (saucers) in Asteroids are drawn as simple shapes: a small flying saucer outline (basically a thin oval with a bubble on top). We will replicate that vector shape for the saucers. Large saucer will be slightly bigger than the small saucer. They should be distinct in size to the player.
	•	Resolution & Scaling: We will design the game at a certain canvas resolution (say 800x600 or 1024x768 pixels) but make it responsive to different screens. The vector nature makes scaling easy without losing quality. We will maintain aspect ratio to avoid distorting the circular wraparound topology. Possibly we’ll letterbox (black bars) if the device screen is far from our base aspect. The important part is that the relative sizes of ship/asteroids/saucer remain consistent. We might define all positions in a virtual coordinate system (e.g., -100 to 100 in both axes like the BYU spec ￼, or 0 to some width/height) and then map to actual canvas pixels. This makes it easier to scale to fullscreen on any device.
	•	Frame Rate: The game will run at a smooth 60 frames per second (or as high as the browser can reliably render) to ensure fluid motion. Original vector monitors had essentially “flicker” but high-persistence phosphor; we will just aim for no stutter in animations.
	•	Animations: Explosions will be depicted by breaking an object into fragments or drawing explosion lines. In Asteroids, an explosion is a brief sequence of lines expanding (the original had a set of pre-defined explosion vector patterns ￼). We can simulate explosions by either particle effects (small line segments flying outward) or quickly scaling a shattered version of the object. This is an implementation detail – at minimum, we will clear the object and possibly flash something to signify it blew up.
	•	UI/HUD: The on-screen text (score, high score, lives) will be drawn in a simple vector font or a pixel font to match the classic look. Typically, the arcade Asteroids showed the score at top left, high score at top center, and number of lives as small ship icons at top left or somewhere visible. We will display:
	•	Score (player’s current score).
	•	High Score (persisted from previous sessions, since we can save it).
	•	Lives remaining (perhaps as little ship icons or just a number of ships left).
	•	We might also display the level/wave number if desired (original didn’t, aside from difficulty just increasing).
	•	Color: The original Asteroids was monochrome (white on black). We will use the same by default. However, some later versions or arcs had colored overlays. We will stick to white vectors on a black background for authenticity. (If we want to get fancy, we could allow an option to change line color or simulate monitor glow with greenish or bluish tint, but not necessary.)
	•	Persistent Elements: Because it’s a web app, we can also include some modern UI touches that do not interfere with gameplay, such as a menu or overlay that can be invoked (for pausing, or showing controls). But during gameplay, the screen will largely be the black field with vectors only.
	•	Responsive to Device Performance: On lower-end mobile devices, we will test that drawing all these lines (especially if many asteroids) is performant. If needed, we could simplify shapes or reduce object count slightly on very small screens. But given the simplicity (just lines), it should be fine on most hardware.

In summary, the graphics system will strive to “look the same” as the original – players should instantly recognize the clone as Asteroids at a glance, thanks to the distinctive vector visuals ￼. We will back this with efficient drawing code so that even though we draw potentially dozens of shapes, it stays smooth.

(For implementation, using the Canvas 2D API’s stroke() calls for each shape every frame is straightforward. Alternatively, we could use WebGL to batch draw lines for potentially better performance with many objects. Given moderate object counts, Canvas 2D in an optimized manner should suffice.)

Audio and Sound Effects

One of the memorable aspects of Asteroids is its sound. The clone will include all the major sound effects from the original game, aiming for exact or very close replicas:
	•	Thrust Sound: A continuous low-frequency rocket noise that plays when the thrust is engaged. In the arcade, this is a looping “hhhhh” sound that starts/stops with thrust. We will include a sound effect for thrust that plays on loop while the player holds the thrust control.
	•	Shooting Sound: Each time the player fires a bullet, a distinctive “pew” or fire shot sound is emitted. We will use a short blip noise for this. (Original Asteroids had a very recognizable shooting sound created by the custom circuitry.)
	•	Explosion Sound: When an asteroid or ship explodes, a “boom” noise is heard. We will have an explosion sound effect for destroying asteroids and a slightly different (maybe louder or with an extra component) explosion for when the player’s ship is destroyed.
	•	Saucer Sounds:
	•	The Large Saucer makes a deep “warbling” tone as it flies (some describe it as a repeating series of beeps at a slow rate).
	•	The Small Saucer has a higher-pitched, faster beeping sound as it moves. These sounds alert the player to the saucer’s presence even off-screen. We will implement these as background looped sounds that play when a saucer is on screen (different loop for large vs small).
	•	Saucer firing sound: could reuse the player’s shooting sound or have its own subtle difference (it might be fine to reuse the pew for simplicity, unless original had a distinct noise).
	•	Heartbeat Background: Asteroids famously has a “heartbeat” soundtrack – a repetitive deep thumping tone that speeds up as the number of asteroids dwindles, creating tension ￼ ￼. At the start of a level, the thumps are slow and far apart. As the player destroys asteroids, the interval between beats shortens, reaching a rapid tempo when only a few asteroids remain (mimicking a heartbeat racing with adrenaline). We will 100% include this feature. Implementation: after each asteroid is destroyed (or at set thresholds of remaining asteroids), we decrease the timer between beats. This can be done by having a base BPM (beats per minute) and increasing it as the count goes down. The sound itself is a low “dum” tone. We can generate or use a sample for it. This background sound adds a lot to the classic feel and intensity, so it’s important to get right.
	•	Extra Life Sound: Gaining a 1UP at 10,000 points in the original often played a quick tune or sound. If a specific sound exists, we’ll include it (or a suitable cue).
	•	Game Start and End: We can include a brief sound when starting the game (like a tone) and maybe a game-over sound or jingle, though Asteroids was a pretty minimalistic game (no music track or anything, just these effects).
	•	Audio Implementation: We will use Web Audio API or HTML5 <audio> elements to play sounds. Because this is a web app, we must handle audio unlocking on mobile (usually require a user interaction before audio can play). We’ll ensure that on first touch or start button, we enable sounds. Sounds can be stored as small audio files (preferably in WAV or OGG for quick playback). Alternatively, some sounds (like thrust or the heartbeat) could be synthesized on the fly with the Web Audio API (since they are simple tones). For accuracy, we might source recordings of the original sound effects (there are resources or MAME samples for Asteroids). Given non-commercial use, using those actual sounds would maximize authenticity.
	•	Volume & Muting: We will provide an option to adjust volume or mute the game, likely via a small on-screen button or settings menu, for user convenience.
	•	Mixing: Multiple sounds can play together (e.g., thrust noise while shooting and heartbeat in background). We must ensure they mix well (no one sound overpowering except maybe the explosion which is intentionally loud). Web Audio API allows control of gain for each source, which we can fine-tune to approximate the original balance.

The sound design is critical for the full nostalgic experience, so we’ll put effort into matching the original sounds. Notably, the original arcade hardware had no dedicated sound chip – instead a custom circuit generated 13 different sound effects ￼. The result was unique analog-like sounds. We might not perfectly recreate the analog quality, but we’ll get as close as possible with digital audio.

Testing will involve listening and comparing to known Asteroids sound profiles and adjusting accordingly. From the thrust rumble to the escalating heartbeat, the audio will significantly enhance the authenticity of our Asteroids clone.

Technical Implementation Details

Technology Stack and Architecture
	•	Platform: The game will be built as a web application using standard web technologies: HTML5, CSS, and JavaScript. It will run in any modern browser. No server component is required for core gameplay (all logic is client-side).
	•	Canvas Rendering: We will use an <canvas> element for rendering the game graphics. The Canvas API provides the needed drawing functions (e.g., moveTo, lineTo, stroke) to draw our vector shapes each frame. This gives us a lot of control for the dynamic line-drawn graphics. The canvas will be sized to fill the screen (maintaining aspect ratio as discussed).
	•	Game Loop: We’ll implement a game loop using requestAnimationFrame in JavaScript. On each frame, we will update game state (object positions, handle input, detect collisions, etc.) and then redraw the entire scene. A target of 60 FPS means each frame has about 16.7ms budget; our logic with relatively few objects should comfortably fit in that.
	•	Object-Oriented Structure: The code will be organized into classes (or JS modules) representing game entities:
	•	Ship class – holds the player ship’s position, velocity, angle, lives, etc. Methods for thrust, rotate, fire, hyperspace, and rendering the ship.
	•	Asteroid class – for asteroids, with properties for position, velocity, rotation angle and spin speed, size (large/med/small), and a method to update position (with wrapping) and render itself.
	•	Saucer class – for UFOs, with properties for position, velocity, type (large/small), shot cooldown, etc., plus update logic (movement, firing) and render method.
	•	Bullet class – for bullets (both player and saucer bullets, possibly distinguished by a flag or subclass), with position, velocity, lifespan counter, and an update (which moves it and decreases lifespan) and draw method.
	•	Game (or GameManager) – orchestrates everything. It keeps track of all active objects in lists/arrays (e.g., asteroids[], bullets[], saucers[], and the single ship). It handles spawning new waves, checking for collisions between objects, updating score/lives, and so on. It also manages the high score table and persistence (if needed).
	•	We might also have a simple Particle or Explosion class if we do more intricate explosion animations.
	•	Collision Detection: We will check collisions each frame or at least at a fixed timestep. Key collisions to check:
	•	Bullets vs Asteroids
	•	Bullets vs Saucers
	•	Saucer bullets vs Ship
	•	Asteroids vs Ship (we can treat the ship as a point with radius or use polygon collision; circle approximation is fine and fast)
	•	Asteroids vs Saucers (saucer destroyed if collision)
	•	(We do not check Asteroid vs Asteroid as noted)
Given potentially many bullets and asteroids, naive collision checks (looping through all pairs) is fine at our scale (e.g., at most 50 asteroids *, plus a few bullets, etc., which is trivial for modern JS). If needed, we can optimize using spatial partitioning, but likely unnecessary.
	•	Physics Constants: We will define constants for things like thrust acceleration, rotation speed, bullet speed, maximum velocity, friction factor, etc. These will be tuned to match the original feel. For instance, the ship’s thrust acceleration and friction will determine how it controls – we want it responsive but also with a bit of drift. We might start with values from known Asteroids clones (e.g., as in the BYU spec: rotate 6° per frame, thrust adds velocity 0.5 per frame, friction such that velocity decays maybe 1-2% per frame).
	•	Random Elements: Initial asteroid directions, saucer spawn times, and saucer shot inaccuracies will use random number generation. We’ll use JavaScript’s Math.random() for these, which is fine for our needs. For consistency (if needed for debugging), we could seed a PRNG, but it’s not necessary.
	•	State Management: The game will likely have a simple state machine (e.g., states like “MENU”, “IN_GAME”, “GAME_OVER/HIGHSCORE_ENTRY”). We’ll implement a basic start screen (maybe just “Click to Start” or similar). After game over, if a high score is achieved, prompt for initials, then show high score list, and possibly allow restarting. Since the user specifically wants the game itself, UI can be minimal.
	•	Persistence: Using the Web Storage API (localStorage), we will save high scores and possibly settings (like sound volume). High scores list can be stored as JSON. This allows the high score table to persist between play sessions (even if you close the browser and come back). As this is a “persistent web app,” offline availability is key (see deployment section).
	•	Performance Considerations: We will ensure that even on phones the game runs without slowdowns:
	•	Use efficient drawing: batch drawing operations when possible (though Canvas 2D doesn’t batch well under the hood, but we will minimize state changes).
	•	Use requestAnimationFrame (which syncs to display refresh and is more efficient than setInterval).
	•	Avoid unnecessary object creation in the main loop (to reduce GC pressure) – reuse objects from pools if needed for bullets, etc.
	•	Use simple math – most of the motion is linear. The occasional Math.sin/cos for rotation (like updating bullet velocity or drawing rotated shapes) is fine. We can cache shape templates and just rotate via matrix transforms if needed for drawing many asteroids.
	•	Test on an average mobile device and optimize if any jank is observed (reducing object count or detail slightly if absolutely needed).
	•	Exactness vs Modern Implementation: While we strive for exact behavior, some internal implementations will naturally differ (we’re writing in JS vs the original’s 6502 assembly). We will verify the gameplay by play-testing against known behaviors: e.g., check that the ship’s movement feels right (does it stop when expected?), that the saucer accuracy and timing feels similar, that the score system matches exactly, etc. If any discrepancy is found (like if our friction is too high and the ship stops too quickly compared to original), we will tweak constants.

Deployment and Persistence
	•	Progressive Web App (PWA): We will make the web app installable on mobile devices as a PWA. This involves providing a Web App Manifest (with name, icons, etc.) and a Service Worker for offline caching. The goal is that the user can “Add to Home Screen” the Asteroids clone on their phone, and launch it full-screen like a native app (no browser chrome). The game should run without internet once cached.
	•	Offline Availability: Using a service worker, we will cache the game’s files (HTML, CSS, JS, images, sound files) on first load. Thereafter, the game can load instantly and run offline – fulfilling the “persistent web app” requirement (it persists on the device).
	•	Cross-Device Compatibility: We will test on Chrome, Firefox, Safari (especially Safari iOS for iPhone), and possibly Chrome on Android. Ensuring the touch controls and performance are good on iPhone and typical Android phones is important for “phone deployments.” Desktop testing on Chrome/Firefox will ensure it works on PC as well.
	•	Responsive Design: As mentioned, the canvas will scale. We might use CSS to ensure if the aspect ratio doesn’t match, we center the game or letterbox it. The UI elements (score, buttons) will be positioned relative to the canvas or screen so they always appear in the correct place.
	•	Data Persistence: High scores and settings will be stored in localStorage so that even if the app is closed, the data remains. This means when the user returns, they’ll still see their high score list. We won’t need server-side database since it’s personal use.
	•	Loading & Initialization: The game assets (like audio files) will be preloaded on first run. We’ll likely show a quick “Loading…” if needed while sounds are fetched. There aren’t many assets (mostly just a few sound files), so load should be quick. The vector graphics require no image assets, which keeps the payload small.
	•	App Size: Expect the entire game to be very lightweight – likely under a few megabytes (mostly due to audio files). Code and graphics themselves are minimal. This suits deployment as a PWA well.
	•	Continuous Play: Because it’s an arcade-style game, users typically play multiple rounds. We will make it easy to restart after game over (e.g., a restart button or just pressing start). We can also have a mechanism to return to a main menu or instructions screen if desired.
	•	Testing and Debugging: We’ll include a debug mode (possibly triggered by URL parameter or key press) to display some info like FPS, object counts, etc., to help ensure everything is working smoothly, especially on mobile.

Additional Considerations
	•	Exactness vs Enhancements: The mandate is an exact copy, so we are avoiding any major gameplay additions or changes that didn’t exist in 1979. This means no power-ups, no new enemy types, no modernized graphics or particle effects beyond what’s needed to mimic the original. Our goal is a true classic experience. One slight concession to modern expectations is adding a pause feature and possibly a simple start menu, but during play the game will behave exactly as the arcade did. We also include the high score name entry which was in the original and is a fun feature.
	•	Two-Player Mode: Original Asteroids allowed 2 players to play alternating turns (not simultaneous co-op). This meant each player took turns after each death. Implementing this is not difficult (it’s basically just a score and lives for Player 2 and swapping control). However, since this is a personal project primarily for single play, we might omit two-player mode initially. If desired, we could include it as an option (e.g., a “Players: 1 or 2” selection at start). For completeness: if 2-player mode is enabled, after Player 1 dies, Player 2 starts with their own lives and score, alternating until both are done. We’ll note this as an optional stretch goal.
	•	Cheats/Settings: The original machines had “DIP switches” for settings (e.g., starting lives 3 or 4, bonus life at 10k or 12k, etc.). We may not expose these in the UI, but we can code default values accordingly. Possibly, for fun, we could allow toggling some settings in a debug panel (like infinite lives cheat for practice, etc.), but that’s not needed for normal use.
	•	Legal Note: Since this is a personal non-commercial clone, using the name “Asteroids” and the original assets (sounds, etc.) is not an issue privately. We will not distribute this commercially. If ever needed, we’d rename it (e.g., “Vector Rocks” or something) and replace assets. But as specified, we are making an exact copy for personal enjoyment, which should be fine.

Conclusion

In summary, this Product Requirements Document outlines a plan to recreate Asteroids (1979) as a web-based game with as much detail and accuracy as possible. The game will feature the same mechanics – the player-controlled triangular ship drifting in a wrap-around 2D field of asteroids and flying saucers, shooting them for points and avoiding destruction ￼. We will match the vector graphic look and even the sounds (including the accelerating heartbeat thump) that made the original so iconic ￼.

By leveraging modern web tech, we’ll deliver the game as a persistent web app that runs offline and is optimized for both desktop and mobile play. The controls will be adapted for touch screens (left/right arrows on left, thrust and fire on right, per the user’s request) while still allowing the precise control needed to navigate asteroid fields and hit targets. All original features from hyperspace to extra lives at 10k will be implemented, yielding an experience virtually identical to popping a quarter into an Asteroids cabinet – except now it’s accessible on your phone or PC at any time.

Through careful attention to gameplay detail (e.g., exact scoring, object behavior) backed by the source references, this PRD ensures that the final product will satisfy any Asteroids enthusiast. The result will be a true clone of the late-70s classic, both in code and graphics detail, suitable for personal nostalgia or introducing new players to a timeless game.
